1. Project Overview & Architecture

What is this project? The College Chat Bot is an AI-powered assistant for TKRCET (TKR College of Engineering & Technology). Students can ask questions in plain English — about admissions, fees, faculty, timings, bus routes, specific student records, placements — and receive intelligent answers in real time.


How does it work? The system uses a combination of Retrieval-Augmented Generation (RAG) — which searches the college website knowledge base — and a SQL system that queries a real student database. An AI language model (Ollama/LLaMA) generates the final human-readable answer.


High-level Architecture:

3. Core: backend.py

backend.pyPython — Main Server

FastAPI Web Server — The Heart of the Chatbot

This is the main entry point of the application. When you run the chatbot, you run this file. It starts a web server that the frontend HTML page talks to.

Key API Endpoints:

Endpoint Method What it does
GET / GET Health check — confirms the server is online
GET /health GET Returns system status (router ready, active sessions)
POST /query POST Main chat endpoint — receives a user message, routes it, returns the answer
GET /session/{id} GET Retrieves the chat history for a given session
DELETE /session/{id} DELETE Clears a specific chat session
GET /sessions GET Lists all active sessions

How the /query endpoint works:

  • Receives the user message + optional session ID
  • Detects intent (general question vs. student database query)
  • If RAG query → streams the response chunk-by-chunk (like ChatGPT typing effect)
  • If SQL query → returns a complete JSON response immediately
  • Logs every interaction to an Excel file via ResponseLogger
📤 Generates / Outputs:
  • Live HTTP REST API at http://127.0.0.1:8000
  • Auto-generated Swagger docs at http://127.0.0.1:8000/docs
  • Passes data to logs/response_log.xlsx via logger
💡 How to run: python backend.py or uvicorn backend:app --reload

4. App / Services Layer

These files live in app/services/ and form the "brain" of the chatbot. Each handles a specific intelligence task.

app/services/query_router.pyPython — Orchestrator

QueryRouter — The Traffic Director

This is the central controller that decides how to answer a question. It holds instances of all three answering systems (RAG, SQL, Deep Chain) and picks the right one based on the intent.

Intent Routes To Example
greeting Instant hardcoded reply "Hi!" → "Hello! I'm your College Buddy 😊"
general UltraRAG System "Who is the principal?"
student SQL System "Students with CGPA > 9"
hybrid Deep Reasoning Chain "Which CSE students are eligible for placement?"
📤 Generates: Returns a Python dict {"response": "...", "source": "...", "accuracy": "..."} back to backend.py.
app/services/intent_detector.pyPython — NLP Classifier

IntentDetector — Understanding What the User Wants (Embeddings-Based)

Uses a multi-tier approach to classify user queries into one of four categories. Keyword-based detection has been removed in favor of AI-powered embeddings.

Detection Pipeline (in priority order):

  1. Regex greetings — instant pattern match for "hi", "hello", etc. (no AI needed)
  2. Gemma 3 1B routing — lightweight AI model (gemma3:1b via Ollama) classifies intent in ~10ms
  3. Semantic similarity fallback — uses all-MiniLM-L6-v2 sentence embeddings to find closest intent by cosine similarity
  4. Default to 'general' — safest fallback if no detection method is available
💡 Recent change: Legacy keyword lists (student_keywords, general_keywords) and the regex-based _regex_detect_intent() method have been removed. All intent detection now uses AI embeddings or the Gemma router.
📤 Generates: Returns a string label — 'greeting', 'student', 'general', or 'hybrid' — used by QueryRouter.
app/services/ultra_rag.pyPython — RAG Engine (946 lines)

UltraRAGSystem — College Knowledge Answering System

This is the largest and most complex file. It handles all general college questions by combining a hardcoded Knowledge Base with semantic search over the scraped website data.

How it answers a question:

  1. Knowledge Base (KB) check first — Checks a hardcoded dictionary of facts (principal name, timings, fees, HODs, etc.). If matched, responds instantly without AI.
  2. Semantic KB match — Uses the all-MiniLM-L6-v2 embedding model to find the closest KB entry using cosine similarity (threshold: 0.55).
  3. ChromaDB retrieval — If KB doesn't have the answer, searches the vector database (built from scraped TKRCET website data) for the top 5 relevant chunks.
  4. Ollama LLM generation — Sends the retrieved context + user query to the LLaMA 3.2 3B model running locally via Ollama API to generate a friendly, conversational answer.

Topic-Based Navigation Links:

The system includes a TOPIC_LINKS mapping of 28 query keywords to real TKRCET website URLs (admissions, departments, placements, syllabus, etc.). When a response is generated:

  • If corpus documents have URLs → those are used as source links
  • If no document URLs exist → _get_topic_links() matches query keywords to relevant TKRCET website pages
  • Links appear as 📌 Quick Links at the top and 📚 Source Links at the bottom of responses
  • Both KB fast-track and RAG streamed responses include navigation links

Knowledge Base covers:

  • Personnel: Principal, Vice Principal, Dean, Secretary, Chairman, all HODs
  • Timings: College hours (9:40 AM – 4:20 PM), lunch break
  • History: Established 2002, JNTUH affiliation, location, campus size
  • Courses: All UG (8) and PG (3) programs
  • Fees: B.Tech, M.Tech, MBA, hostel, transport fees
  • Facilities: Transport routes, canteen, labs, hostels
  • Activities: NCC, NSS, cultural fest SISIR, technical fest MEDHA
  • Accreditations: NAAC A+, NBA, AICTE, UGC 2(f) & 12(B)
  • Statistics: Injected from SQL database at startup (total/placed students)
📤 Generates:
  • Plain text answers (from KB — instant) with topic navigation links
  • Streamed token-by-token answers (from Ollama LLM) with Quick Links and Source Links
  • Navigation link chips rendered by the frontend from matched TKRCET website URLs
app/services/sql_system.pyPython — SQL Query Engine

SQLSystem — Student Database Query Handler (with Safety Filter)

Connects to app/database/students.db (SQLite) and answers questions about students. Converts natural language into SQL queries either via regex entity extraction or via an LLM (Llama 3.2:3b model via Ollama).

Query processing pipeline:

  • Entity extraction: Detects roll number, branch (17 aliases including CSE-AIML, CSE-DS, CSM, MBA), name, CGPA condition, placement status, gender from the query text
  • SQL generation: Builds a SELECT query from extracted entities OR asks Llama 3.2:3b to write the SQL
  • Safety filter (_validate_sql()): Blocks destructive operations (DROP, DELETE, ALTER, UPDATE, INSERT, TRUNCATE). Only allows SELECT queries targeting the students table. Enforces LIMIT 1000 cap.
  • Post-validation: Both LLM-generated and regex-built queries pass through the safety filter before execution
  • Privacy protection: Returns only aggregate summaries (counts, averages) for general queries — never dumps individual student records
  • Special cases: Top recruiting companies query, context-aware follow-up questions

Supported department aliases:

CSE, CSE-AIML (AI/ML/artificial intelligence), CSE-DS (data science), CSM, ECE (electronics), EEE (electrical), ME (mechanical), CE (civil), IT (information technology), MBA (management)

Student table columns handled:

ROLL NO, NAME, BRANCH, CGPA, ATTENDANCE, COMPANY PLACED, GENDER, SECTION, YEAR, PASSED YEAR, SEMESTER

📤 Generates: Formatted text summary like "Summary (45 students found): • Placed: 38 out of 45 • Average CGPA: 8.2 • Top recruiters: TCS, Infosys…"
app/services/chain.pyPython — LangChain Agent

DeepReasoningChain — Hybrid AI Agent for Complex Questions

Used for hybrid queries that need both RAG and SQL together. Uses LangChain's ReAct agent pattern: the AI thinks step-by-step about which tool to call.

  • Tool 1 — CollegeKnowledge: Wraps UltraRAG for general info
  • Tool 2 — StudentDatabase: Wraps SQLSystem for student data
  • The agent uses LLaMA 3.2 3B (via Ollama) to decide which tool to call, read the result, and combine into a final answer
  • Falls back to plain RAG if the agent fails
📤 Generates: A combined natural language answer that may pull from both the knowledge base and the student database.
app/services/logger_service.pyPython — Logging

ResponseLogger — Dual-Sheet Conversation Log Writer

Automatically records every interaction the chatbot has into logs/response_log.xlsx. The file contains two separate sheets with different purposes:

Production Sheet — 6 columns (every live query)

Column Description
Timestamp Date and time of the interaction
User Query Exact text the user typed
Bot Response Full answer the bot gave
Time Taken (s) Pure server-side processing time (does NOT include network)
Session ID UUID identifying the conversation session
Source Which system answered: RAG / SQL / KB

Evaluation Sheet — 13 columns (populated by prompt_test.py)

Column Description
Timestamp When the test was run
Prompt The test question
Bot Answer Full response from the chatbot
Source RAG / SQL / KB
Retrieval Confidence (%) Cosine similarity of query vs top retrieved chunk × 100
Latency (s) Client-side round-trip time (server + network)
Server Time (s) Server-side processing time echoed inside the API response
Faithfulness % (LLM) Are all claims grounded in the retrieved context? (LLM judge, weight 30%)
Relevance % (LLM) Does the answer address the question? (LLM judge, weight 25%)
Completeness % (LLM) Are all aspects of the question covered? (LLM judge, weight 20%)
BERTScore F1 % Semantic sentence-level overlap: answer vs context (weight 15%)
Link Validity How many hyperlinks in the answer are live (e.g., 3/4 Valid)
Accuracy % Weighted final score across all metrics
📤 Generates: logs/response_log.xlsx with two sheets:
  • Production — grows with every live chat interaction
  • Evaluation — populated by prompt_test.py with full metric scores
💡 Run python tools/refresh_logs.py to archive the current log and start fresh. Check logs/Metrics_Reference.pdf for a full explanation of every metric.

7. Scripts — The Data Pipeline

These files live in scripts/ and are run once (or periodically) to prepare data for the chatbot. They are NOT part of the live server.

scripts/tkrcet_scraper.pyPython — Step 1: Smart Scraper

TKRCET AI-Powered Scraper (Groq + Playwright)

The first step in the modern data pipeline. Reads a list of TKRCET website URLs from tkrcet_links.txt, opens each page with a headless Chromium browser (Playwright), extracts clean text, and uses the Groq API to structure it into JSON.

  • Uses 4 parallel threads for fast scraping
  • Waits 2 seconds per page for JavaScript to load
  • Structured extraction: targets <main>, <article>, .content containers instead of raw body text
  • Noise removal: strips nav, footer, header, script, style, sidebar elements
  • Extracts headings (h1-h3) separately for context
  • Idempotent: clears output file before writing; URL deduplication within each run
📤 Generates: all_results.json — a comprehensive JSON file containing structured sections for every page on the college website.
⚠️ Requires Groq API Key + Playwright. Run: python scripts/tkrcet_scraper.py
scripts/prepare_data.pyPython — Step 1.5: Data Flattener

RAG Data Preparation Script

Converts the complex nested JSON output from the AI scraper into a flattened text format suitable for vectorization. Ensures that every section and list item is correctly preserved as searchable text.

📤 Generates: app/database/vectordb/scraped_data.jsonl — serves as the transition point to the vectorization pipeline.
scripts/ingest.pyPython — Step 2: Vector DB Builder

ChromaDB Ingestion Script

The second step. Takes the scraped JSONL data and stores it in ChromaDB (the vector database) using semantic chunking. This makes the data searchable by meaning, not just keywords.

  • Uses SemanticChunker (LangChain) with percentile breakpoint — splits text at meaning-change boundaries
  • Embeddings: all-MiniLM-L6-v2 (384-dimension vectors)
  • Adds contextual prefix to each chunk: "Title: … Source: …"
  • Processes in batches of 100 to avoid memory overflow
  • Deletes and recreates the collection each run for clean rebuilds
📤 Generates: app/database/vectordb/chroma/ — the ChromaDB persistent vector store used by UltraRAG at runtime.
⚠️ Must run AFTER scrape.py. Run: python scripts/ingest.py
scripts/corpus_converter.pyPython — Format Converter

Corpus Format Converter (JSON → JSONL)

Converts the vector data from a unified JSON array format into the line-delimited JSONL format expected by the UltraRAG system. Each output line contains: {"id": "doc_0", "contents": "...", "metadata": {...}}.

Also has a --verify option that checks each line of the output for correctness.

📤 Generates: app/database/vectordb/corpus_ultrarag.jsonl — loaded by UltraRAGSystem at startup to list available documents.
Run: python scripts/corpus_converter.py --verify
scripts/generate_vectors.pyPython — Step 1.5: Vector Generator

Unified Vectors Generator

Reads scraped_data.jsonl and data/rawdata/faq_rows.json, chunks text content with sentence-boundary splitting and overlap, deduplicates, and outputs the master unified_vectors.json file.

  • Idempotent: overwrites output file on each run
  • Text cleaning: removes nav/footer noise, normalizes whitespace
  • Chunking: 500-character max with 50-char overlap at sentence boundaries
📤 Generates: app/database/vectordb/unified_vectors.json — consumed by corpus_converter.py.
Run after scrape.py: python scripts/generate_vectors.py
scripts/cleanup_database.pyPython — Data Refinement

Database Cleanup & FAQ Enhancer

This is the primary maintenance tool for unified_vectors.json. It fixes data inaccuracies that a scraper might miss or pull incorrectly.

  • Data Fixes: Corrects specific facts (e.g., resolving PhD year conflicts, removing repetitive navigation menus).
  • FAQ Injection: Injects high-priority FAQ entries for key personnel (Principal, HODs, Secretary) to ensure 100% accuracy.
  • Cache Reset: Deletes old FAISS/BM25 indices to force the system to rebuild them with the new cleaned data.
📤 Generates: A cleaned version of unified_vectors.json (and a .backup file). Use this to "push" manual data fixes into the system.
scripts/clear_vectordb.pyPython — Maintenance

Vector Database Cleaner

Deletes the ChromaDB collection content so you can start fresh. Use this before re-running ingest.py if you want a clean rebuild of the vector database.

📤 Generates: Removes data from app/database/vectordb/chroma/. Nothing is created.

9. Frontend

frontend/index.htmlHTML/CSS/JS — UI (≈40 KB)

Chatbot Web Interface

The complete front-end of the chatbot — a single HTML file that contains HTML structure, CSS styling, and JavaScript all-in-one. Runs in the user's browser.

  • Renders a chat window with send button, message bubbles, and typing indicators
  • Sends user messages to POST /query on localhost:8000
  • Handles Server-Sent Events (SSE) streaming — displays AI response word-by-word as it arrives
  • Manages session IDs for conversation continuity
  • Renders markdown formatting (bold, bullet points, links) in responses
  • Navigation Link Chips: Extracts Quick Links and Source Links from responses using extractLinks() and renders them as styled clickable chip elements via renderLinkChips() — works for both SSE streaming and non-streaming responses

Link Chip System:

  • extractLinks(text) — Parses response text for link blocks (Quick Links, Source Links, Related Links, etc.) and standalone URLs. Returns clean text + extracted link objects.
  • renderLinkChips(container, suggestions) — Creates styled 🔗 chip elements as <a> tags with target="_blank" and appends them below the response.
  • For streaming responses: links are extracted after the stream completes (data.done event) and chips are rendered below the final response.
  • For non-streaming responses: links are extracted and rendered inline when the message bubble is created.
📤 Generates: The visual chat interface displayed in the browser. Sends API requests to backend.py and displays the responses with interactive navigation link chips.
💡 Open this file directly in a browser after starting backend.py.

docs/chunking.mdMarkdown — Technical Doc

Dual-Stage Text Chunking Strategy

Documents the sophisticated two-part approach used to balance speed and semantic accuracy:

  • Stage 1: Sentence-Boundary Chunking (in generate_vectors.py) — Splits text into ~500 character blocks using punctuation breaks to preserve readability. Includes a 50-character overlap to maintain context across boundaries.
  • Stage 2: Semantic Chunking (in ingest.py) — Uses LangChain's SemanticChunker to analyze the meaning of sentences. It breaks chunks when the underlying topic changes (percentile breakpoint), ensuring logical grouping for the database.
  • Contextual Enrichment: Every chunk is prepended with its Page Title and Source URL so the AI never loses the context of a fact.
docs/Embeddings_SqlDB.mdMarkdown — Technical Doc

Machine Learning Embeddings: all-MiniLM-L6-v2

Every piece of text in our system (scraped pages, FAQs, student questions) is converted into a Vector Embedding using the all-MiniLM-L6-v2 model.

  • What are Embeddings? They are a list of 384 numbers that represent the mathematical meaning of a sentence. This allows the bot to understand that "fee structure" and "how much is the cost" mean the same thing.
  • Why all-MiniLM-L6-v2? It is the industry standard for lightweight, local RAG. It is extremely fast (runs on CPU) while being remarkably accurate at capturing semantic meaning.
  • System Roles:
    • Vector DB: Stores college knowledge vectors for retrieval.
    • Intent Detection: Compares the user's question to "template" vectors for Student queries vs. General queries to decide which system to use.

16. What to Run & In What Order

# Command What it does Run when
1 pip install -r requirements.txt Install all dependencies First time setup only
2 ollama pull llama3.2:3b Download LLaMA AI model First time setup only
3 ollama pull gemma3:1b Download Gemma 3 model (for evaluation judge) Optional (for testing only)
4 python scripts/scrape.py Scrape TKRCET website pages First time & when site updates
5 python scripts/generate_vectors.py Generate unified_vectors.json from scraped + FAQ data After scraping
6 python scripts/cleanup_database.py Fix data issues & inject FAQs To apply manual knowledge fixes
7 python scripts/corpus_converter.py Convert to UltraRAG format (JSONL) After vector generation or cleanup
8 python scripts/ingest.py Build the ChromaDB vector database After corpus conversion
9 ollama serve Start the Ollama AI model server Every time before running backend
10 python backend.py Start the FastAPI web server Every time you want to use the chatbot
11 Open frontend/index.html Launch the chat UI in browser After backend is running

17. Troubleshooting & Common Issues

Common Errors & Solutions

Problem Cause Solution
ModuleNotFoundError Missing Python libraries Run pip install -r requirements.txt in your virtual environment.
503 Service Unavailable Systems failed to initialize Check terminal for errors. Usually caused by missing dependencies or Ollama being offline.
Connection Error (Ollama) Ollama is not running Run ollama serve in a separate terminal and ensure models are pulled.
✗ Error initializing systems Missing data/models Run python scripts/ingest.py and ensure llama3.2:3b is pulled.
💡 Tip: Always ensure your virtual environment is activated (.venv\Scripts\activate) before running any script.
